# Development guidelines

- Use Git only for read-only inspection. Do not run any Git operation that writes or mutates state, including staging, committing, amending, checking out or switching branches, restoring, resetting, cleaning, stashing, merging, rebasing, cherry-picking, reverting, fetching, pulling, pushing, or modifying branches, tags, remotes, configuration, or worktrees. Do not bypass this restriction by directly modifying Git metadata or using other tools to perform equivalent Git mutations. Ordinary source-file edits are allowed.
- Add type annotations to arguments and return values of new or modified Python functions and methods, including nested functions. Use type aliases for complex shared types.
- In docstrings, start each array argument or return value description with its shape, before its dtype or explanatory text (for example, `actions: (B,) int32 action IDs` and `prior_logits: (B, A) float32 masked policy logits`). Apply this to array-valued fields within structured returns as well.
- Treat type annotations as the source of truth for internal Python APIs. Rely on static typing rather than adding defensive runtime checks or tests for values excluded by the declared types (for example, checking for `None` when an argument is annotated as `jax.Array`). Validate untyped external input at system boundaries. Keep runtime validation for constraints annotations cannot express, including dtypes, value ranges, and relationships between arguments; cover internal array shape contracts with tests as described below.
- Do not use `chex` or `src/rl2/shape_checker.py` to check array shapes in production code. Instead, ensure focused pytest coverage of array shape contracts, including expected output shapes and relevant input shape variations and boundary cases. Tests may use `chex`, `src/rl2/shape_checker.py`, or plain assertions to check array shapes.
- Run `uv run ruff format <changed-python-files>` on Python files you change before finishing. Follow the Ruff configuration in `pyproject.toml` and avoid formatting unrelated files.
- Use pytest for tests: write pytest test functions and run targeted checks with `uv run pytest <test-path>` or specific test node IDs.
- Maintain meaningful test coverage for new and changed behavior. Add or update tests for normal operation, relevant edge cases and boundary conditions, and expected error handling; assert observable behavior rather than mirroring implementation details.
- For bug fixes, add a regression test that fails before the fix and passes afterward whenever practical. Keep tests deterministic and independent, and use parametrization when it makes related cases clearer.
- Keep tests fast without weakening meaningful coverage. Extend existing tests when they already exercise the relevant behavior; consolidate duplicate cases and remove redundant tests only when distinct behaviors, edge cases, and regression coverage remain covered.
- Use the smallest models, array shapes, batch sizes, datasets, rollout lengths, and training step counts that reliably exercise the behavior under test. Do not run full end-to-end training in tests. Test the functions used by training scripts directly (for example, rollout collection, individual updates, checkpoint serialization, and logging); mock training when testing CLI wiring.
- Parametrize only when each case covers a distinct behavior, boundary, error path, or known regression. Use one representative per equivalence class; do not sweep arbitrary sizes, seeds, numeric values, or multiple values that produce the same rounded result. Give non-obvious cases a descriptive ID or a short comment explaining their unique coverage.
- Do not stack parametrizations for independent concerns. Test each concern once, adding combinations only for meaningful interactions. Check scalar configuration arithmetic and validation directly; do not initialize or execute a model for every scalar case. Keep one representative integration test for wiring, and avoid repeating a full update or rollout for options already covered by focused unit tests.
- For JAX tests, reuse shapes and dtypes where practical to reduce repeated tracing, lowering, and compilation, while retaining cases that specifically test shape or dtype differences. A populated disk compilation cache does not eliminate tracing and lowering costs in a new process.
- Avoid unnecessary expensive setup, repeated computation, network access, and disk I/O in unit tests. Reuse expensive immutable fixtures where safe, keep mutable state isolated, and use lightweight fakes for dependencies outside the behavior under test. Retain focused integration tests for interactions that require real dependencies.
- Run only tests covering behavior affected by the changes, including directly affected callers and relevant integrations. Changes to shared code or multiple components require identifying the affected tests, not automatically running the full suite. Run the full suite only when explicitly requested by the user. After further edits, rerun only tests affected by those edits or needed to investigate a failure; do not repeat unaffected passing tests. Documentation-only changes do not require tests unless they change executable examples or tested behavior. Report the checks run and any failures or coverage gaps, including tests that could not be run.
